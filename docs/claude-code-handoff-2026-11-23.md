Multilang의 한국어 프로필은 유지한다. 이 메모 작성 중 사용자별 `Enable=0`으로 네 프로필을 비활성화했다. 이는 Windows 사용자 계정의 CTF/TSF 프로필 레지스트리 설정이며, OS 업데이트/언어 설정 변경 후 다시 활성화될 수 있다. 사용자가 입력기 선택 메뉴에서 실제로 사라졌는지 확인 필요.
한국어 Microsoft IME는 다시 활성화함.

## A0 회귀 보고
`docs/next-tasks.md`의 A0은 Win32 옛 입력칸(CUAS 경유)에서 조합이 키마다 끊기는 문제를 기록하고 있다. 사용자의 추가 관찰:

> 재부팅하고 나니 모든 입력칸에서, 옛 입력칸 방식을 쓸 필요가 없는 입력칸에서도, 옛 입력칸과 똑같이 동작함.

기존 A0에는 메모장은 정상이고 WinForms TextBox 등 옛 입력칸에서만 `d → k → s` 식으로 프리뷰가 한 글자씩 들어간다고 적혀 있었으므로, 이번 관찰은 입력칸 분류/기능 감지 또는 TSF 경로 선택에 더 넓은 회귀가 생겼다는 뜻일 수 있다. 재현 단계와 실제 입력 동작의 의미를 사용자와 확인하고, 전역적으로 옛 입력칸 처리로 빠지는 원인을 조사할 것. 재부팅과 Meltype 설치 시점을 함께 고려하되 아직 인과관계는 미확정.

## A0 후속 수정 및 문자표 재확인 (2026-11-23)

앞선 수정에서 `TS_SS_TRANSITORY`만으로 조합 창을 켜면 일반 입력칸까지 옛 입력칸처럼 보일 수 있어 `Edit`/WinForms 창 클래스만 확인하도록 좁혔다. 그러나 이 조건은 Windows 기본 문자표의 실제 TSF 컨텍스트에서 Edit 자식 창을 놓쳐, 원래 A0 증상(`dkssud`가 조합되지 않고 `d`, `k`, `s` 등 키 단위로 들어감)이 다시 발생했다.

수정 (`tip/src/lib.rs`, `legacy_floating`):
- `Edit` 및 `WindowsForms10.Edit` 계열 창/부모는 조합 창 모드로 처리한다.
- 포커스 창 탐색에 더해 TSF 활성 뷰의 HWND도 확인한다.
- 위 창 클래스 탐색으로 판별하지 못해도, `TS_SS_TRANSITORY` 문맥이 표준 대화상자(`#32770`) 안에 있으면 조합 창 모드로 처리한다. 이는 문자표 같은 CUAS 입력칸을 잡기 위한 보조 조건이다.
- 일반 입력칸은 입력칸 안 조합을 유지한다. 사용자는 일반 입력칸이 정상임을 확인했다.

검증:
- 릴리스 빌드 성공 후 새 `deploy/x64/multilang_tip.dll` 배포.
- 문자표를 완전히 닫았다 다시 열어 새 DLL을 로드한 뒤 `dkssud` 입력: 입력칸에는 키가 들어가지 않고 조합 창에 `안녕`이 표시됨.
- Space 확정 후 문자표 입력칸에 `안녕`이 들어가는 것을 확인.
- 문자표 외 모든 CUAS 앱은 아직 검증하지 않음. 추가 회귀가 있으면 입력 컨트롤의 TSF 상태와 창 계층을 비교한다.

## 옛 입력칸(A0) 최종 판별 수정 상세 (2026-11-23)

### 증상과 원인
- Win32/CUAS 옛 입력칸은 한국어 IME에서 조합을 입력칸 내부에 직접 표시하면 키마다 조합이 끝나 `d`, `k`, `s`처럼 로마자 키가 하나씩 들어갈 수 있다. 이 경로에서는 조합을 입력칸 대신 별도 조합 창에 표시하고, 확정 시 입력칸에 전달해야 한다.
- 처음에는 `TS_SS_TRANSITORY`만으로 옛 입력칸을 판별했으나, 이 플래그만으로 분류하면 일반 입력칸도 옛 입력칸 모드로 빠질 수 있었다.
- 그다음 `Edit`/`WindowsForms10.Edit` 창 클래스만 확인하도록 좁히자 일반 입력칸은 정상화됐지만, Windows 기본 문자표(CharMap)는 TSF 콜백 스레드에서 포커스된 Edit 자식 창을 찾지 못해 A0 동작이 재발했다.

### 적용한 수정
`tip/src/lib.rs`의 `legacy_floating(context)`에서 옛 입력칸을 다음 순서로 판별한다.
1. 현재 포커스 HWND와 그 부모 계층(최대 8단계)에서 `Edit` 또는 `WindowsForms10.Edit` 계열을 찾는다.
2. 찾지 못하면 TSF 활성 뷰의 HWND와 그 부모 계층도 같은 방식으로 검사한다.
3. 두 경로에서 Edit를 못 찾더라도, 문맥이 `TS_SS_TRANSITORY`이고 포커스 또는 활성 뷰의 부모 계층에 표준 대화상자 클래스 `#32770`이 있으면 옛 입력칸으로 판정한다. 문자표의 CUAS 경로를 위한 보조 판별이다.
4. 그 외에는 입력칸 내부 TSF 조합을 유지한다. 따라서 일반 입력칸을 전역적으로 조합 창 모드로 돌리지 않는다.

`apply()`는 이 판별 결과가 참일 때만 조합 문자열을 `candwin::show_floating`으로 표시하고, 비어 있거나 포커스 문맥이 바뀌면 조합 창을 정리한다. 일반 TSF 입력칸에서는 기존처럼 조합을 문서에 반영한다.

### 확인 결과 및 한계
- 사용자가 일반 입력칸은 정상 동작한다고 확인했다.
- Windows 기본 문자표를 완전히 종료한 뒤 다시 열고 `dkssud`를 입력했을 때, 입력칸에는 키 단위 로마자가 들어가지 않고 조합 창에 `안녕`이 표시됐다. Space로 확정하면 문자표 입력칸에 `안녕`이 전달됐다.
- 문자표 외 다른 CUAS/Win32 앱은 아직 검증하지 않았다. 회귀가 생기면 각 앱에서 `GetFocus`, TSF 활성 뷰 HWND, 부모 창 클래스, `TS_SS_TRANSITORY`를 비교한다.
- 검색창 통합 롤백 후 재부팅을 완료했다. 배포 DLL `deploy/x64/multilang_tip.dll`의 SHA-256은 검색 직전 백업과 같은 `D3C55B4E8C531CAC277CCAB433EB1A25920E2AEAA429C3CAA6C56F9C32E0FA0A`이며, 재부팅 예약도 남아 있지 않다. 사용자는 현재 작동에 문제가 없다고 확인했다.
