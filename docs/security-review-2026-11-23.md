# Multilang IME 보안 검토

- 검토일: 2026-11-23
- 검토 범위: 프로젝트 소스, named pipe IPC, TSF 입력 보호, 사용자 데이터 저장, UIAccess 후보창, 설치·릴리스 설정
- 검토 방식: 소스와 설정에 대한 정적 검토 4회
- 상태: 개선 권고 문서. 코드 수정 또는 런타임 침투 시험은 수행하지 않음

## 요약

현재 코드 검토에서 출시 전 우선 확인할 항목이 발견됐다. named pipe 요청 크기와 동시 연결이 제한되지 않아 서비스 거부가 가능하고, 비밀번호 입력 보호는 입력 범위 확인 실패 시 fail-open으로 동작한다. 앱 컨테이너에 넓게 허용한 파이프 접근 권한으로 `ClearLearning` 명령도 호출할 수 있으며, UIAccess 후보창은 허용된 `WM_COPYDATA` 메시지의 발신자를 검증하지 않는다.

코드 서명 인증서는 UIAccess 실행과 게시자 신뢰에 필요하지만, 위 항목을 해결하지는 않는다. 이 문서는 정적 검토 결과이므로 실제 영향과 앱별 동작은 Windows 환경에서 확인해야 한다.

## 발견 사항

### R1. IPC 요청 크기 및 동시 연결 제한 부재

- 심각도: 높음
- 위치: `backend/src/main.rs`의 `read_message` 및 `CreateNamedPipeW`
- 근거: 메시지를 64 KiB 버퍼로 반복해서 읽어 `Vec`에 무제한 누적한다. 파이프 인스턴스 수는 `PIPE_UNLIMITED_INSTANCES`이고 연결마다 새 스레드를 만든다.
- 영향: 파이프에 접근 가능한 클라이언트가 큰 메시지를 보내거나 다수의 연결을 열면 백엔드 메모리·스레드를 소진시켜 입력기 응답을 멈추게 할 수 있다.
- 개선 권고:
  1. IPC 프로토콜 최대 요청 크기를 정하고 상한을 넘으면 즉시 연결을 닫는다.
  2. 동시 연결 또는 작업 스레드 수를 제한한다. 제한 초과 시 새 연결을 거절한다.
  3. `Hello.app` 등 문자열 필드와 JSON 중첩도 적절한 길이로 제한한다.
  4. 상한에서 정확히 거부되는지와 큰 메시지에서 메모리가 누적되지 않는지 테스트한다.

### R2. 입력 범위 확인 실패 시 IME 보호가 fail-open

- 심각도: 중간~높음
- 위치: `tip/src/lib.rs`의 `input_off`, 특히 `RequestEditSession`과 입력 범위 해석
- 근거: 범위 확인 세션에 오류가 나면 `false`를 반환해 입력기를 끄지 않는다. 세션 호출 자체는 성공했더라도 범위 속성을 얻지 못하면 빈 목록으로 처리한다. 또한 여러 입력 범위가 보고될 경우 첫 항목만 검사한다.
- 영향: 앱이 비밀번호/PIN 용도를 제공하지 않거나 속성 조회가 실패하는 입력칸에서는 IME가 계속 키를 처리할 수 있다. 이 경우 조합과 학습 경로로 입력이 처리될 가능성이 있다. 모든 앱에서 비밀번호 자동 차단이 보장된다고 볼 수 없다.
- 개선 권고:
  1. 비밀번호/PIN 범위 판별을 실패한 경우의 정책을 명시한다. 보안 우선이라면 해당 컨텍스트에서는 IME를 끄는 fail-closed 동작을 고려한다.
  2. 여러 입력 범위 중 하나라도 보호 범위면 끄도록 검토한다.
  3. 표준 Win32, WinForms, 브라우저, Chromium/Electron, UWP/앱 컨테이너의 비밀번호 입력칸에서 실제 동작을 확인한다.
  4. 차단이 확인되지 않은 앱이나 입력칸이 있으면 사용자 문서의 보장 문구를 조정한다.

### R3. 앱 컨테이너가 `ClearLearning`으로 학습 데이터를 삭제 가능

- 심각도: 중간
- 위치: `backend/src/pipe_security.rs`의 DACL, `backend/src/main.rs`의 요청 처리, `backend/src/session.rs`의 `clear_learning`
- 근거: 파이프 DACL은 샌드박스 앱 호환을 위해 `ALL APPLICATION PACKAGES` 및 관련 앱 그룹에 읽기/쓰기 권한을 허용한다. 요청 처리에서 `ClearLearning` 명령은 추가 권한 확인 없이 실행되며 언어 판정 이력, 한자 학습, Mozc 사용자 학습을 지운다.
- 영향: 해당 파이프에 접근 가능한 앱 컨테이너 클라이언트가 사용자의 지속 학습 데이터를 삭제할 수 있다. 코드에서 이 명령으로 데이터 열람이 되는 것은 확인하지 못했다.
- 개선 권고:
  1. 이 명령이 TIP 이외 클라이언트에 노출되어도 되는지 결정한다.
  2. 가능하면 IPC 연결 클라이언트를 구분·검증하거나, 학습 삭제를 별도의 사용자 승인된 경로로 제한한다.
  3. 앱 컨테이너 허용이 필수라면 키 입력 처리와 사용자 데이터 관리 명령을 분리해 권한을 최소화한다.

### R4. UIAccess 후보창의 메시지 발신자 미검증

- 심각도: 중간
- 위치: `candhost/src/main.rs`의 `WM_COPYDATA` 처리 및 `ChangeWindowMessageFilterEx`
- 근거: 후보창 프로세스는 `uiAccess=true`를 사용하고 `WM_COPYDATA`를 받도록 UIPI 필터를 완화한다. 메시지 본문 크기(1 MiB 미만)는 제한하지만 발신자 프로세스나 창을 확인하지 않는다. 처리된 `show` 명령은 전달된 문자열을 후보창에 표시한다.
- 영향: 메시지를 보낼 수 있는 같은 데스크톱 프로세스가 임의 내용을 UIAccess 후보창에 표시해 화면을 가장하거나 사용자에게 잘못된 안내를 보여줄 수 있다. 검토한 코드에서 이를 통해 명령 실행이나 임의 파일 접근이 가능하다는 증거는 확인하지 못했다.
- 개선 권고:
  1. 메시지 발신자 프로세스/창을 확인하고 허용된 경로만 처리한다.
  2. 가능하면 발신자 인증이 가능한 IPC로 메시지 전달 방식을 변경한다.
  3. 입력 문자열 길이와 후보 수에 별도 상한을 두어 UI 처리 비용을 제한한다.
  4. UIAccess를 계속 사용할 경우 모든 메시지 처리 경로를 높은 신뢰 경계로 검토한다.

### R5. 원격 named pipe 클라이언트 명시적 거부 없음

- 심각도: 낮음(방어 심화 권고)
- 위치: `backend/src/main.rs`의 `CreateNamedPipeW`
- 근거: 파이프 생성 플래그에 원격 클라이언트 거부 설정이 보이지 않는다. 현재 DACL이 접근을 제한하므로, 이번 정적 검토만으로 원격 접속이 성공한다고 단정하지 않는다.
- 영향: 로컬 전용 IPC라는 설계 의도가 API 설정에서 명시적으로 강제되지 않는다.
- 개선 권고: 원격 클라이언트 거부 플래그를 적용하고, 동일 머신과 원격 경로 모두에서 접속이 거절되는지 검증한다. DACL 및 세션 범위도 함께 점검한다.

## 인증서와 배포

후보창 빌드 설정은 `uiAccess=true`를 요청한다. Windows UIAccess 요구 사항상 실행 파일은 Authenticode로 서명되어야 하고, Program Files와 같은 보호된 위치에서 실행되어야 한다. 현재 설치기가 Program Files에 설치하도록 구성되어 있으므로, 추후 인증서 발급과 서명은 후보창 기능을 켜는 데 필요하다.

서명은 게시자와 파일 무결성 확인에 도움을 주지만 R1~R5의 입력 검증이나 접근 제어를 대체하지 않는다. 공개 배포 전에는 최종 산출물 서명, 서명 검증, 해시 제공, 업데이트 파일 출처 검증 절차를 함께 마련한다. 설치 스크립트가 관리자 권한으로 실행되므로, 사용자가 실행하는 패키지와 스크립트도 신뢰 가능한 출처에서 받아 검증하는 배포 절차가 중요하다.

## 확인된 방어

- 설치기는 Program Files를 기본 설치 위치로 사용한다.
- 앱 컨테이너에는 설치 폴더의 읽기·실행 권한을 추가하며, 해당 변경만으로 쓰기 권한을 부여하는 코드는 확인되지 않았다.
- 설치·제거 로직은 매니페스트 상대 경로를 검증하고, 설치 폴더 내 지정 파일 중심으로 작업하도록 설계되어 있다.
- 후보창 메시지는 1 MiB 미만인지 확인한 뒤 JSON 파싱한다.
- Mozc 도우미 응답은 64 MiB 상한을 둔다.

이 항목들은 확인된 일부 방어이며, 설치/제거 스크립트의 전체 동작이나 런타임 보안을 보증하지 않는다.

## 권장 작업 순서

1. R1: IPC 메시지 크기 및 동시 연결 제한.
2. R2: 비밀번호/PIN 범위 확인 실패 정책을 정하고 실제 앱에서 검증.
3. R3: 앱 컨테이너 권한에서 `ClearLearning` 명령 분리 또는 보호.
4. R4: UIAccess 후보창 메시지 발신자 확인과 입력 제한.
5. R5: named pipe의 원격 접속 명시적 거부.
6. 공개 배포 전에 UIAccess 실행 파일 서명 및 릴리스 검증 절차 적용.

## 범위 및 한계

이번 검토는 2026-11-23 현재 읽을 수 있었던 소스와 설정을 대상으로 수행했다. 동적 분석, 퍼징, Windows ACL 실측, 코드 서명 검증, 설치/업데이트/제거 시나리오 시험은 수행하지 않았다. 따라서 심각도는 검토된 코드 경로에서 예상되는 영향 기준이며, 실제 악용 가능성은 대상 Windows 버전과 설치 환경에서 추가 확인해야 한다.

검토 당시 저장소에 설치·릴리스 파일 변경 사항이 있었으며, 이 문서는 저장소 기본본이 아니라 해당 시점의 작업 트리 상태를 기준으로 한다.
