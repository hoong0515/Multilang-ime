# Multilang IME 보안 재검토

- 검토일: 2026-11-24
- 대상: 최신 작업 트리의 TSF 입력 보호, named pipe IPC, 사용자 학습 데이터, UIAccess 후보창, 배포 산출물
- 방식: 소스·설정 정적 검토 및 `dist` 실행 파일 서명 상태 확인
- 코드 변경: 없음
- 동적 보안 시험: 수행하지 않음

## 요약

이전 검토에서 지적한 IPC 요청 크기·동시 연결 제한, 원격 클라이언트 거부, `ClearLearning` 권한 검사는 코드에 반영됐다. 다음 세 가지 위험은 남아 있다.

1. 비밀번호 입력 범위 확인이 실패하거나 비어 있으면 입력기를 끄지 않는 fail-open 경로가 남아 있다.
2. AppContainer에 열린 파이프에서 키 입력과 확정을 허용하므로, 신뢰되지 않은 패키지 앱이 공용 언어 판정 학습 기록을 오염시킬 수 있다.
3. UIAccess 후보창은 포그라운드 실행 파일 이름만 검사하고 `WM_COPYDATA` 발신자를 인증하지 않아, 이름을 위장한 프로세스가 후보창에 임의 문자열을 띄울 수 있다.

또한 현재 `dist`의 프로젝트 실행 파일과 DLL은 서명되지 않았다. UIAccess 후보창을 포함하는 배포 패키지는 Authenticode 서명 및 Program Files 설치 조건을 만족하는지 확인하기 전까지 출시 준비가 완료됐다고 볼 수 없다.

## 발견 사항

### R1. 입력 범위 판별 실패 시 IME가 계속 동작함

- 심각도: 높음
- 위치: `tip/src/lib.rs`의 `input_off`
- 근거: `RequestEditSession`이 오류를 반환하면 `false`를 돌려 입력기를 끄지 않는다. 호출은 성공했지만 범위 조회 결과가 비어 있어도 보호 입력칸이 아닌 것으로 취급한다. 비밀번호/PIN 용도는 범위 목록에 하나라도 있으면 차단하도록 개선됐다.
- 영향: 앱이 비밀번호 `InputScope`를 제공하지 않거나 범위 조회가 실패하는 경우 입력이 IME의 조합·확정·학습 경로로 들어갈 수 있다. 표준 Win32/WinForms의 일부 컨트롤 스타일 검사는 있지만 모든 사용자 지정 컨트롤을 포괄하지 않는다.
- 권고: 조회 실패·빈 결과의 보안 정책을 명시하고, 비밀번호 입력칸에서 보안 우선 동작을 적용할지 검토한다. 브라우저, Chromium/Electron, WinForms, UWP/AppContainer 및 사용자 지정 컨트롤에서 실제 차단 여부를 확인한다. 확인되지 않은 앱에 대해 비밀번호 자동 차단을 보장한다고 안내하지 않는다.

### R2. AppContainer 클라이언트가 공용 언어 학습 이력을 오염시킬 수 있음

- 심각도: 중간~높음
- 위치: `backend/src/pipe_security.rs`, `backend/src/main.rs`, `backend/src/session.rs`
- 근거: 파이프 DACL은 AppContainer 패키지 그룹에 읽기·쓰기 권한을 준다. 관리 명령 `ClearLearning`은 AppContainer 또는 Low Integrity 클라이언트에서 거부하도록 개선됐다. 그러나 요청 처리에서 `Key`를 클라이언트 유형별로 제한하지 않으며, 입력을 확정하면 공용 `History`에 기록하고 `%LOCALAPPDATA%\\multilang-ime\\history.json`에 저장한다.
- 영향: 파이프에 접근 가능한 패키지 앱이 가짜 입력과 확정을 보내 사용자의 지속적인 언어 판정 선호 기록을 바꿀 수 있다. 이는 다른 클라이언트의 판정 결과에도 영향을 줄 수 있다.
- 권고: 앱 컨테이너에서 반드시 필요한 입력 기능과 지속 학습을 분리한다. 학습 기록을 클라이언트별로 격리하거나, 신뢰 가능한 TIP 경로임을 확인할 수 있는 IPC 권한 설계를 검토한다. 단순히 `Hello.app` 값을 신뢰해 권한을 부여하지 않는다.

### R3. UIAccess 후보창의 발신자 검증 우회 가능성

- 심각도: 중간
- 위치: `candhost/src/main.rs`의 `shell_in_foreground` 및 `WM_COPYDATA` 처리
- 근거: `WM_COPYDATA`는 UIPI 필터에서 허용된다. `show`는 메시지 크기, 후보 수, 문자열 길이를 제한하고 셸 프로세스가 포그라운드일 때만 표시하도록 개선됐다. 하지만 포그라운드 프로세스 검사는 전체 경로·서명·프로세스 ID가 아닌 실행 파일 basename만 비교한다. 메시지 발신자 창도 검증하지 않는다.
- 영향: 셸 실행 파일과 같은 basename을 사용한 다른 프로세스가 포그라운드일 때 조건을 통과할 수 있다. 해당 프로세스는 UIAccess 후보창에 조작한 내용을 표시해 검색 UI 위에 가짜 안내나 후보처럼 보이는 문구를 덮을 수 있다. 정적 검토에서 이를 명령 실행이나 파일 접근으로 연결하는 경로는 확인하지 않았다.
- 권고: 셸 프로세스를 basename만으로 식별하지 말고 신뢰된 전체 경로·서명 등을 확인한다. 가능하면 발신자를 인증할 수 있는 IPC로 메시지 전달을 바꾸고, UIAccess 경계로 들어오는 모든 명령을 최소화한다.

### R4. 연결 수는 제한됐지만 유휴 파이프 연결은 오래 점유 가능

- 심각도: 낮음~중간
- 위치: `backend/src/pipe.rs`의 `MAX_CONNECTIONS` 및 `read_message`
- 근거: 요청은 16KiB, 연결은 최대 128개이며 원격 클라이언트를 거부한다. 이는 이전의 무제한 메시지 누적 및 연결별 스레드 생성 위험을 크게 줄였다. 다만 연결별 요청 읽기에는 유휴 시간 제한이 없다.
- 영향: 파이프에 접근 가능한 클라이언트가 연결을 열고 데이터를 보내지 않은 채 연결 128개를 점유하면, 정상 TIP의 신규 연결이 거부될 수 있다. 공격은 로컬 사용자 또는 허용된 AppContainer 경계 안에 한정된다.
- 권고: 연결 수 제한은 유지하고, 유휴 클라이언트 정리 또는 세션 상한을 더 낮출 필요가 있는지 검토한다. 실제로 정상 TIP 연결 수가 최대치에 근접하는지도 확인한다.

## 해소된 이전 발견 사항

- **요청 크기 무제한 누적:** 요청 상한 `MAX_REQUEST = 16 KiB` 및 초과 메시지 연결 종료가 추가됐다.
- **연결·스레드 무제한 생성:** 동시 연결 상한 `MAX_CONNECTIONS = 128`과 슬롯 제한이 추가됐다.
- **원격 named pipe 클라이언트:** `PIPE_REJECT_REMOTE_CLIENTS` 플래그가 적용됐다.
- **AppContainer의 `ClearLearning`:** 클라이언트 토큰을 검사해 AppContainer 또는 Low Integrity 요청을 거부한다. 단, 같은 사용자 권한의 Medium 이상 데스크톱 프로세스는 여전히 이 명령을 보낼 수 있다.
- **후보창 메시지 입력 제한:** 메시지 64KiB, 후보 수, 문자열 길이 제한과 셸 포그라운드 조건이 추가됐다. 발신자 인증은 여전히 필요하다.

## 서명 및 배포 확인

현재 `dist`에서 확인한 서명 상태:

| 산출물 | 상태 |
|---|---|
| `MultilangIME-CandWin.exe` | NotSigned |
| `multilang_tip.dll`, `backend.exe`, 설정 실행 파일, Mozc helper | NotSigned |
| 번들 VC 런타임 DLL | Valid |

후보창 빌드는 `uiAccess=true`를 요청한다. Microsoft 문서에 따르면 UIAccess 실행 파일은 신뢰된 Authenticode 서명이 필요하고 관리자만 쓸 수 있는 보호된 위치에 설치돼야 한다. 설치기는 Program Files를 기본 위치로 쓰지만, 현재 확인된 미서명 후보창 실행 파일은 이 서명 요건을 충족하지 않는다. 서명 후 최종 패키지에 대해 서명 검증과 설치 위치·실행 동작을 확인해야 한다.

참고: [Microsoft UIAccess 보안 요구사항](https://learn.microsoft.com/en-us/windows/win32/winauto/uiauto-securityoverview)

## 권장 조치 순서

1. 비밀번호/PIN 입력 범위 조회 실패 및 빈 결과의 정책을 결정하고 실제 앱에서 검증한다.
2. AppContainer의 키 입력 요청이 공용 학습 데이터를 변경할 수 있는 설계를 검토하고 학습 격리 방안을 정한다.
3. UIAccess 후보창의 발신자 인증과 셸 프로세스 식별을 강화한다.
4. 유휴 파이프 연결의 점유 시간을 제한할 필요가 있는지 확인한다.
5. 배포 전에 서명된 최종 패키지를 만들고 UIAccess 실행·설치 경로를 검증한다.

## 범위와 한계

이번 검토는 2026-11-24 작업 트리의 소스·설정에 대한 정적 검토다. `dist` 바이너리의 Authenticode 서명 상태는 로컬에서 조회했지만, 악성 클라이언트 모의 시험, AppContainer ACL 실측, 퍼징, 비밀번호 입력 앱별 시험, 서명 후 UIAccess 실행 검증은 수행하지 않았다. 심각도는 코드 경로에서 예상되는 영향에 따른 우선순위이며 실제 도달 가능성과 Windows 버전별 차이는 추가 검증이 필요하다.
